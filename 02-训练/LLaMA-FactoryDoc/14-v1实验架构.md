# 14 — v1 实验架构

`src/llamafactory/v1/` 是 `0.9.6.dev0` 中与 v0 并存的实验架构。它不是 v0 的薄封装：配置、数据格式、Trainer、分布式和插件系统都重新实现。启用方式是：

```bash
USE_V1=1 llamafactory-cli sft examples/v1/train_lora/train_lora_sft.yaml
```

## 1. 入口切换

唯一公共入口是 `src/llamafactory/cli.py::main()`：

```text
USE_V1 未开启 → src/llamafactory/launcher.py
USE_V1=1      → src/llamafactory/v1/launcher.py
```

v1 launcher 当前识别：

| 命令 | 实现 |
|---|---|
| `train`、`sft` | `v1.trainers.sft_trainer.run_sft()` |
| `dpo` | `v1.trainers.dpo_trainer.run_dpo()` |
| `rm` | `v1.trainers.rm_trainer.run_rm()` |
| `chat` | `v1.samplers.cli_sampler.run_chat()` |
| `merge` | `v1.plugins.model_plugins.peft.merge_and_export_model()` |

`env` 和 `version` 在 v1 launcher 中仍抛 `NotImplementedError`；没有 v0 的 `api/export/webchat/webui` 路由。帮助文本只展示 sft/version，少于实际已有命令，因此应以 `_DIST_TRAIN_COMMANDS=("train","sft","dpo","rm")` 和分支代码为准。

多设备时 v1 launcher 同样自动重启 torchrun，但会把子命令明确转发给 `launcher.py`。这是与 v0 子进程直接默认调用 `run_exp()` 的重要差异。

## 2. 分层结构

```text
v1/
├── launcher.py
├── config/        # 新 dataclass + OmegaConf/HfArgumentParser
├── accelerator/   # 设备、DP/CP mesh、collective
├── core/          # ModelEngine/DataEngine/BaseTrainer/BaseSampler
├── plugins/
│   ├── data_plugins/
│   ├── model_plugins/
│   └── trainer_plugins/
├── trainers/      # SFT/RM/DPO
├── samplers/      # CLI sampler
└── utils/         # registry、类型、日志、回调、环境
```

依赖方向是 `trainers → core → accelerator/plugins/config → utils`。与 v0 的 `train → data/model → hparams → extras` 不共享主流程。

## 3. 配置系统

`v1/config/arg_parser.py::get_args()` 返回：

```text
ModelArguments, DataArguments, TrainingArguments, SampleArguments
```

支持三类输入：

1. YAML/YML：OmegaConf 读取，后续命令行采用 `key=value` 覆盖；
2. JSON：同样先转 OmegaConf 再覆盖；
3. 普通 CLI 参数：HfArgumentParser。

`ALLOW_EXTRA_KEYS=1` 可忽略多余字段，默认遇到 v0 遗留参数会报错。解析后立即调用 `set_seed()`。

v1 配置大量使用具名子配置：

```yaml
dist_config:
  name: fsdp2
optim_config:
  name: adamw
lr_scheduler_config:
  name: cosine
peft_config:
  name: lora
kernel_config:
  name: liger_kernel
```

`name` 用作插件 registry 的键。示例是理解有效 schema 的第一来源：`examples/v1/`。

## 4. 插件注册机制

基类是 `v1/utils/plugin.py::BasePlugin`。它维护：

```text
_registry[name][method_name] = callable
```

插件通过装饰器注册：

```python
@SomePlugin("implementation_name").register()
def implementation(...):
    ...
```

调用 `SomePlugin("implementation_name")(...)` 会转发到 `__call__` 注册项；也可注册 `save_model` 等命名方法。

当前插件族：

- 数据：`DataLoaderPlugin`、`DataConverterPlugin`；
- 模型：`PeftPlugin`、`QuantizationPlugin`、`KernelPlugin`、`InitPlugin`；
- 并行：sequence parallel / Ulysses；
- Trainer：`DistributedPlugin`、`OptimizerPlugin`、`LRSchedulerPlugin`；
- batching/rendering template 也采用可替换组件。

这比 v0 的大量 if/elif 和工具函数更显式地支持扩展，但 registry 是进程内全局状态，插件模块必须被 import 才会完成注册。

## 5. DataEngine

`v1/core/data_engine.py::DataEngine` 本身就是 PyTorch Dataset：

```text
__init__(dataset_path)
  → _get_dataset_info()
  → _load_dataset()
  → _build_data_index()
__getitem__()
  → _convert_data_sample()
```

`train_dataset` 可指向：

- 本地 `dataset_info.yaml`；
- Hugging Face Hub 上的 YAML；
- 本地文件/目录；
- Hub dataset id。

YAML 中每个数据集可定义 `path/source/split/streaming/size/weight/converter`。非 `hf_hub` source 交给 `DataLoaderPlugin`；`converter` 交给 `DataConverterPlugin`。`size/weight` 通过 `adjust_data_index()` 重采样。

与 v0 的区别：

- v0 先把 dataset 映射为 stage-specific tokenized dataset；
- v1 DataEngine 保持模型无关，返回标准 `Sample`；
- 渲染、tokenization、动态 batching 后移到 `Renderer` 与 `BatchGenerator`；
- streaming 数据目前 `__len__()` 返回 -1，索引访问和 `__iter__()` 尚未完整实现。

## 6. ModelEngine

初始化链：

```text
ModelEngine(model_args, is_train=True)
  → AutoProcessor
  → Renderer(template, processor)
  → AutoConfig
  → 选择初始化设备/Meta
  → QuantizationPlugin（可选）
  → AutoModelForCausalLM/ImageTextToText/TokenClassification
  → PeftPlugin（可选）
  → KernelPlugin（可选）
```

模型类由 `ModelClass` 决定：

- `LLM`：因果 LM 或 image-text-to-text；
- `CLS`：`AutoModelForTokenClassification`，RM 将 `num_labels=1`；
- 其他：`AutoModel`。

DeepSpeed ZeRO-3 模型加载由 `plugins/model_plugins/deepspeed_utils.py` 建立初始化上下文。`init_on_meta` 与 LoRA、量化存在显式限制。全参训练把模型转 float32；PEFT 由具名插件创建。

## 7. BaseTrainer

`v1/core/base_trainer.py::BaseTrainer` 完全不继承 HF Trainer。初始化顺序：

```text
BatchGenerator
→ 计算 training steps
→ activation checkpointing
→ DeepSpeed：先建 engine/optimizer/scheduler，再 prepare
  或 FSDP2/DDP：先 shard model，再 optimizer/scheduler
→ checkpoint coordinator
→ callbacks/state
→ 可选 sequence parallel plugin
```

训练循环 `fit()` 自己实现：

1. `BatchGenerator` 每次返回一个 optimizer step 所需的多个 micro-batch；
2. 计算全局有效 token 数；
3. 按 token 数和 DP size 缩放每个 micro-batch loss；
4. DeepSpeed 由 engine backward/step；其他后端直接 backward；
5. gradient clipping、optimizer/scheduler step；
6. all-reduce loss/grad norm；
7. callback 日志和 checkpoint。

这套逻辑使 `global_batch_size`、`micro_batch_size` 和动态/padding-free batching 成为一等概念，不依赖 HF `gradient_accumulation_steps`。

分布式路径：

- `dist_config=None` 且 world size>1：DDP；
- `name=fsdp2`：`trainer_plugins/distributed/fsdp2.py`；
- `name=deepspeed`：`trainer_plugins/distributed/deepspeed.py`；
- `cp_size>1`：安装 sequence parallel，要求 FlashAttention 2；Qwen3.5 暂不支持。

checkpoint 由 `core/utils/checkpoint.py::TrainingCheckpointCoordinator` 统一协调；`save_ckpt_as_hf` 会增加保存时内存消耗。

## 8. 三个 Trainer

### 8.1 SFT

`SFTTrainer.compute_loss()` 使用 Renderer 产生的 `loss_weights`：

```text
loss = sum(-token_logp * loss_weight) / sum(loss_weight)
```

完整链：

```text
run_sft → DistributedInterface → DataEngine → ModelEngine
→ SFTTrainer.fit → save_model → destroy
```

### 8.2 RM

`run_rm()` 把 `model_class` 改成 `CLS`，检查 pair 数据，初始化 score head。RM 将 chosen 和 rejected 包在同一序列中，以 `token_type_ids` 的 1/2 表示文档边界，构造各自重置的 `position_ids`，取两段最后 token 的 score：

```text
L = -logσ(chosen_score - rejected_score)
```

当前 RM 明确不支持 `cp_size>1`；DDP 使用 `find_unused_parameters=True`。

### 8.3 DPO

`v1/trainers/dpo_trainer.py::DPOTrainer` 本地实现 reference、logp 提取和损失。支持：

- `sigmoid`：`compute_sigmoid_dpo_loss()`，支持 label smoothing；
- `orpo`：`_odds_ratio_loss()`；
- `simpo`：`_simpo_loss()`。

`v1/config/training_args.py` 的 `pref_loss` Literal 只有这三种，不支持 v0 的 `hinge/ipo/kto_pair`。DPO 对 chosen/rejected 的处理同样利用 `token_type_ids` 文档索引，并收集 reward/logp/logit 指标到 `_step_metrics`。

## 9. v0 与 v1 对照

| 维度 | v0 默认架构 | v1 实验架构 |
|---|---|---|
| 启用 | 默认 | `USE_V1=1` |
| Trainer | HF Trainer/TRL 子类 | 自研 `BaseTrainer` |
| 配置 | 5 组 hparams dataclass | 4 组新 dataclass + 具名子配置 |
| 数据 | stage processor 预处理 | DataEngine + Renderer + BatchGenerator |
| 扩展 | 工具函数/条件分支 | `BasePlugin` registry |
| 分布式 | HF Accelerate/Trainer 为主 | 自研 interface + DS/FSDP2 plugin |
| stage | PT/SFT/RM/PPO/DPO/KTO | SFT/RM/DPO |
| 偏好损失 | 6 种 | sigmoid/orpo/simpo |
| UI/API | 完整 | 无 |
| 推理 | HF/vLLM/SGLang/KT/API | CLI sampler |
| 模板 | `data/template.py` 大注册表 | model template plugins + Renderer |

## 10. 当前成熟度与迁移注意

1. v1 是实验路径，不能假设 v0 YAML 兼容；默认会拒绝未知字段。
2. v1 尚无 PT、PPO、KTO trainer，也无 WebUI/API/export 命令；`merge` 替代部分 export 用途。
3. v1 的 `version/env` 未实现，因此检查项目版本应临时关闭 `USE_V1`。
4. v1 依赖 Transformers v5 风格（如 `dtype`、processor 和 document-index mask），运行环境要求高于传统 v0 配置。
5. v1 示例和 `tests_v1/` 是行为依据，特别是 FSDP2 DPO、损失精度、Ulysses、kernel 和 checkpoint 测试。
6. 不应在生产配置上仅通过加 `USE_V1=1` 做“原地迁移”；应从 `examples/v1/` 重建配置并逐项验证。
