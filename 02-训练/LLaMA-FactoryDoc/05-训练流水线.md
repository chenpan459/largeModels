# 05 — 训练流水线源码分析

> 对应源码版本：LLaMA Factory `0.9.6.dev0`。本文分析默认的 v0 架构（`src/llamafactory/train/`），不把实验性 `USE_V1=1` 流程混入其中。

## 1. 从 CLI 到训练函数

训练命令最终进入 `src/llamafactory/train/tuner.py`：

```text
llamafactory-cli train config.yaml
  → cli.py / launcher.py
  → 单卡：run_exp()
  → 多卡：launcher.py 重新执行 torchrun ... launcher.py train ...
  → 每个 rank 调用 run_exp()
```

`launcher.py` 在 `command == "train"` 且满足以下任一条件时启动 `torchrun`：

- `FORCE_TORCHRUN=1`；
- 检测到多设备，且没有启用 Ray、KTransformers。

多机参数来自 `NNODES`、`NODE_RANK`、`NPROC_PER_NODE`、`MASTER_ADDR`、`MASTER_PORT`；设置 `RDZV_ID` 时走 elastic rendezvous，并支持 `MIN_NNODES`、`MAX_NNODES`、`MAX_RESTARTS`。因此 `run_exp()` 自身不是多进程启动器：普通 DDP 的进程由 `launcher.py` 创建，每个进程独立执行同一条训练调用链。

## 2. `run_exp()` 与 Ray 分支

`run_exp(args=None, callbacks=None)` 的精确职责是：

1. `read_args(args)` 将 Python 字典、CLI 参数或 YAML/JSON 路径规范化；
2. 遇到 `-h/--help` 时调用 `get_train_args()` 输出参数帮助；
3. `get_ray_args(args)` 只解析 Ray 配置；
4. `callbacks = callbacks or []`；
5. `use_ray=True` 时调用 `_ray_training_function(ray_args, {"args": args, "callbacks": callbacks})`，否则直接调用 `_training_function(...)`。

Ray 路径位于同一文件下部。它初始化 Ray、检查集群设备数、确定 head IP/端口、创建 placement group，按节点 IP 排序 bundle，然后为每个 rank 创建 `Worker` actor。Worker 设置分布式环境变量和 `LOCAL_RANK`，再回调模块级 `_training_function()`。主进程等待所有 actor 完成后 `ray.shutdown()`。

注意两种分布式模式的差异：

- `torchrun`：外层 CLI 启动进程，训练结束后 `_training_function()` 尝试 `dist.destroy_process_group()`。
- Ray：actor 内部执行同一 workflow；若 Ray 已初始化，函数在清理进程组前直接返回，由 Ray 负责销毁。

## 3. `_training_function()`：参数、回调与 stage 路由

`_training_function(config)` 首先调用：

```text
get_train_args(args)
  → model_args
  → data_args
  → training_args
  → finetuning_args
  → generating_args
```

随后按固定顺序扩展回调列表：

1. 始终加入 `LogCallback`；
2. `pissa_convert=True`：`PissaConvertCallback`；
3. `use_swanlab=True`：`get_swanlab_callback(...)`；
4. `early_stopping_steps != None`：Transformers `EarlyStoppingCallback`；
5. `enable_torch_profiler=True`：`TorchProfilerCallback`；
6. `profile_modules` 非空：`ModuleProfilerCallback`；
7. 最后加入 `ReporterCallback`。

调用者传入的回调保留在列表前部。`ReporterCallback` 被刻意放到最后，但 Trainer 自己仍可能追加 stage 专用回调。

路由优先级不是单纯按 stage：

```text
pt/sft + use_hyper_parallel
  → train/hyper_parallel 的 run_pt/run_sft
否则 pt/sft/dpo + use_mca
  → train/mca 的 run_pt/run_sft/run_dpo
否则
  pt  → train/pt/workflow.py::run_pt
  sft → train/sft/workflow.py::run_sft
  rm  → train/rm/workflow.py::run_rm
  ppo → train/ppo/workflow.py::run_ppo
  dpo → train/dpo/workflow.py::run_dpo
  kto → train/kto/workflow.py::run_kto
```

HyperParallel 只覆盖 PT/SFT；MCore Adapter 只覆盖 PT/SFT/DPO。开关与 stage 不匹配时会落回默认 workflow，而不是报“后端不支持”。

## 4. 所有默认 workflow 的共同骨架

六个 workflow 基本共享以下调用顺序：

```text
load_tokenizer(model_args)
  → {"tokenizer": tokenizer, "processor": processor_or_none}
get_template_and_fix_tokenizer(tokenizer, data_args)
get_dataset(template, ..., stage=..., **tokenizer_module)
load_model(tokenizer, ..., is_trainable=training_args.do_train)
构造 stage 专用 collator / ref model / reward model
构造 Trainer
train / evaluate / predict
保存模型、指标、state、模型卡
```

模板修复必须在 `load_model()` 前执行，因为它可能添加 EOS、PAD、stop words；模型加载阶段再依据 `resize_vocab` 调整 embedding。

### 4.1 PT

`run_pt()` 使用 `stage="pt"`、`DataCollatorForLanguageModeling(mlm=False)` 和 `CustomTrainer`。训练后保存模型、metrics、state；评估时根据 `eval_loss` 计算 perplexity。若 `eval_on_each_dataset=True`，分别产生 `eval_{name}_loss/perplexity`。

### 4.2 SFT

`run_sft()` 是最完整的路径：

1. 数据以 `stage="sft"` 处理；
2. `use_asft_loss=True` 时 `create_ref_model()`；
3. 构造 `SFTDataCollatorWith4DAttentionMask`，传入模板、模型、padding、`block_diag_attn`、`neat_packing`、attention 实现和计算 dtype；
4. `predict_with_generate=True` 使用 `ComputeSimilarity`，否则可选 `ComputeAccuracy + eval_logit_processor`；
5. 把生成参数、所有 EOS/附加特殊 token 和 PAD ID 交给 `CustomSeq2SeqTrainer`；
6. 执行 train/eval/predict。

量化模型仅做预测时，会设置 `_hf_peft_config_loaded=True` 兼容 PEFT 预测。KTransformers 当前不支持 SFT 的 `predict_with_generate` 或 `compute_accuracy`。生成式预测前 tokenizer 切为左 padding。

### 4.3 RM

`run_rm()` 实际把数据传给 `get_dataset(..., stage="rm")`，因此要求 `dataset_info.json` 中 `ranking=true`。模型以 `add_valuehead=True` 加载，collator 为 `PairwiseDataCollatorWithPadding`，Trainer 为 `PairwiseTrainer`，指标为 chosen/rejected accuracy。

保存时除普通 decoder/adapter 外，还通过 `fix_valuehead_checkpoint()` 把 `v_head.*` 拆到 `value_head.safetensors` 或 `value_head.bin`。

### 4.4 DPO

源码中的重要细节是：`run_dpo()` 调用 `get_dataset(..., stage="rm")`，不是 `"dpo"`。数据层的 stage 类型本身也没有 `dpo`，DPO 与 RM 共享 pairwise processor 和 `ranking=true` 校验。

`use_ref_model=True` 时创建 reference model；LoRA 且未显式配置 reference model 时，`create_ref_model()` 可返回 `None`，由 DPO Trainer 利用禁用 adapter 的基座作为参考。评估模式且没有独立 reference model 时，可直接令 `ref_model = model`，随后移除无法解释的 reward 指标。

### 4.5 KTO

`run_kto()` 使用 `stage="kto"`、`KTODataCollatorWithPadding` 和 `CustomKTOTrainer`。processor 同时产生目标样本、KL 样本和 `kto_tags`。无独立 reference model 且仅评估时可以复用当前模型。

### 4.6 PPO

`run_ppo()` 使用无监督 processor（`stage="ppo"`），策略模型带 value head，并把 tokenizer 切到左 padding以便 rollout。随后：

- `create_ref_model(..., add_valuehead=True)` 创建参考策略；
- `create_reward_model()` 支持 `api`、`lora`、完整模型三种奖励来源；
- `CustomPPOTrainer.ppo_train()` 执行自定义训练循环；
- 保存后修复 value-head checkpoint。

完整奖励模型必须与策略模型共享 tokenizer 和词表。LoRA 奖励模型会挂到同一 pretrained model 的 `"reward"` adapter，并将奖励 head 参数注册为 buffer。

## 5. Trainer 级回调

`tuner.py` 的全局回调之外，各 Trainer 还追加：

- `SaveProcessorCallback`：存在 processor 时，在每个 checkpoint 和最终输出目录保存 processor；
- RM/PPO 的 `FixValueHeadModelCallback`：每次 checkpoint 保存后拆分 decoder 与 value head；
- `BAdamCallback`：`use_badam=True` 时加入；
- Transformers 默认回调：由 Trainer 或 PPO 的 `DEFAULT_CALLBACKS` 提供。

关键回调行为：

- `LogCallback`：只在 `args.should_save` 的进程写 `trainer_log.jsonl`；异步单线程落盘，记录进度、loss、reward、吞吐和可选显存峰值；WebUI 模式还可响应中止信号。
- `PissaConvertCallback`：训练开始保存 `pissa_init`，结束生成 `pissa_backup` 与标准 LoRA 差分 `pissa_converted`，然后恢复可训练 adapter。
- `ReporterCallback`：仅 world process zero 向 W&B、Trackio、SwanLab 注入四组参数配置。
- `TorchProfilerCallback`：每个 rank 写独立 trace 目录。
- `ModuleProfilerCallback`：用通配符匹配模块并注册 forward/backward hooks，仅支持 CUDA/NPU event 计时。

## 6. 同步、缓存与主进程语义

数据加载和 tokenization 包在两段 `training_args.main_process_first(...)` 中。`data_shared_file_system=False` 时使用本机优先语义；共享文件系统时使用全局主进程优先，避免多节点同时写缓存。非主 rank 的 datasets `map()` 强制允许读取缓存，即便用户设置了覆盖缓存。

模型与 Trainer 仍在每个 rank 独立构造；Accelerate/Transformers 在 Trainer 初始化后包装 DDP、FSDP 或 DeepSpeed。最终绘图使用 `trainer.is_world_process_zero()`，常规保存依赖 `training_args.should_save`。

## 7. 扩展点

- 新训练阶段：在 `train/{stage}/workflow.py` 实现编排，在 `tuner.py` 增加路由，并同步扩展参数校验与数据 processor 分派。
- 自定义 Trainer：保持接受 `**dataset_module`、`**tokenizer_module` 和 callbacks，避免丢失 eval dict、多模态 processor 保存能力。
- 自定义回调：通过 `run_exp(..., callbacks=[...])` 注入；它会先于内置回调出现在列表中。
- 新参考/奖励策略：扩展 `trainer_utils.py::create_ref_model/create_reward_model`。
- 特殊分布式后端：参考 HyperParallel/MCA，在默认 stage 路由之前截获。

## 8. 常见陷阱

1. `DatasetModule` 只有 `train_dataset`、`eval_dataset` 两个可选键，没有 `predict_dataset`；预测直接使用 `eval_dataset`。
2. DPO 数据层 stage 是 `"rm"`，不要寻找不存在的 `stage="dpo"` processor。
3. `callbacks = callbacks or []` 会在传入空列表时创建新列表；传入非空列表则会被原地追加内置回调。
4. 早停需要评估策略与最佳指标配置配合，仅设置 `early_stopping_steps` 不足以产生有效早停。
5. RM/PPO 的 value head 必须通过专用修复逻辑保存；直接把 TRL wrapper 的 state dict 当普通模型导出会产生错误键名。
6. `resume_from_checkpoint` 交给 Trainer；LoRA adapter 的恢复/合并规则则由模型模块另行处理，两者不是同一层机制。
7. Ray、torchrun、HyperParallel、MCA 是互相有优先级的执行路径，不能仅凭 YAML 中某个开关推断最终后端。
