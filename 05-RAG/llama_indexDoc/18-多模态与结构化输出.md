# 18 - 多模态与结构化输出

> 版本范围：`llama-index-core 0.14.23`。本版本正处于从专用 MultiModal API 向统一 `LLM + ContentBlock` 迁移的阶段。

## 1. 三层模型

多模态链路可分为：

1. **数据层**：`ImageNode`、`ImageBlock`、`ChatMessage.blocks`
2. **检索/查询层**：双向量库、文本到图像/图像到图像召回、把 blocks 交给 LLM
3. **结构化输出层**：`BasePydanticProgram`、Function Calling 或 Pydantic parser

不要混淆：

- `ImageNode` 是索引/存储节点；
- `ImageBlock` 是直接发送给 LLM 的消息内容块；
- Program 负责把模型输出变成 Pydantic 对象，它不负责建立多模态索引。

## 2. ImageNode 与 ImageBlock

### 2.1 ImageNode

源码：`llama-index-core/llama_index/core/schema.py:852`。

`ImageNode(TextNode)` 可保存：

- `image`：base64 字符串
- `image_path`
- `image_url`
- `image_mimetype`
- `text`：caption/OCR/描述
- `embedding`
- `text_embedding`

`resolve_image()` 优先级是 `image -> image_path -> image_url`；URL 会通过 `requests.get()` 拉取。`hash` 同时考虑图像来源和 text。

`get_content_blocks()` 会将图像解析成 `ImageBlock`，并附加 metadata blocks。旧参数 `image_resource` 在构造器中会被兼容转换为 path/url/mimetype。

`ImageDocument(Document)` 位于 `schema.py:1330`，本质上是带文档语义的 ImageNode 兼容类型。

### 2.2 ImageBlock

源码：`llama-index-core/llama_index/core/base/llms/types.py:304`。

它是 LLM 消息层对象：

- `image: bytes | IOBase`
- `path`
- `url`
- `image_mimetype`
- `detail`

validator 会做 base64/mimetype 处理；`resolve_image()` 负责解析实际内容。发送给统一 LLM 接口时，通常使用：

```python
from llama_index.core.llms import ChatMessage, TextBlock, ImageBlock

message = ChatMessage(
    role="user",
    blocks=[
        ImageBlock(path="./invoice.png"),
        TextBlock(text="提取发票号码和总金额"),
    ],
)
response = llm.chat([message])
```

这代表 0.14.23 的新方向：多模态能力由 `ChatMessage.blocks` 表达，而不是必须使用完全独立的 LLM 类型。

## 3. MultiModalLLM 旧抽象与统一 LLM

专用抽象位于 `core/multi_modal_llms/base.py`：

- `MultiModalLLMMetadata`
- `MultiModalLLM`

它定义 `complete(prompt, image_documents)`、`chat(messages)` 及流式/异步版本，并通过 `llm_chat_callback`、`llm_completion_callback` 自动加入 Callback 与 Instrumentation。

但 0.14.23 的实际代码也大量接受普通 `LLM`，只要实现支持 `ImageBlock` 的 chat。判断模型是否多模态不能只靠 Python 类型：`MultiModalVectorStoreIndex.as_query_engine()` 甚至通过 `class_name()` 是否包含 `"multi"` 发 warning，这只是启发式检查。

建议新代码优先：

- 使用具体集成提供的统一 `LLM`；
- 用 `ChatMessage(blocks=[...])` 传文本和图像；
- 仅在维护旧集成时直接依赖 `MultiModalLLM` 抽象。

## 4. MultiModalVectorStoreIndex

源码：

- `indices/multi_modal/base.py`
- `indices/multi_modal/retriever.py`
- `embeddings/multi_modal_base.py`

该索引维护两个命名空间：

```text
StorageContext.vector_stores
  ├─ "default" -> 文本向量库
  └─ "image"   -> 图像向量库
```

构建流：

```text
nodes
  ├─ TextNode（ImageNode 有 text 时也进入）
  │    -> 普通 text embed_model
  │    -> default vector store
  └─ ImageNode
       -> MultiModalEmbedding.get_image_embedding
       -> image vector store
```

默认 `image_embed_model="clip:ViT-B/32"`。`is_image_to_text=True` 时还会用普通 text embedding 重算 ImageNode 的 text，并在当前实现中把 `_image_embed_model` 替换为 `_embed_model`；这是兼容逻辑，不等同于真正同时保留两套 embedding。

若 vector store 不存文本，或 `store_nodes_override=True`，索引会清除 embedding 后把 Node 写入 docstore/index struct，查询时再回填。

## 5. MultiModalVectorIndexRetriever

核心入口：

```text
retrieve(text query)
  ├─ _text_retrieve
  │    -> 普通文本 embedding -> default store
  └─ _text_to_image_retrieve
       -> multimodal text encoder -> image store
  -> 拼接结果（不做跨模态统一重排）
```

独立方法：

- `text_retrieve()`
- `text_to_image_retrieve()`
- `image_to_image_retrieve()`
- 对应异步版本

`image_to_image_retrieve(path)` 会构造 `QueryBundle(query_str="", image_path=path)`，使用 `embedding_image[0]` 经图像编码器查询 image store。

参数：

- `similarity_top_k`：文本结果数
- `image_similarity_top_k`：图像结果数
- `filters`、`doc_ids`、`node_ids`
- `vector_store_query_mode`、`alpha`、`sparse_top_k`

两路相似度来自不同 embedding 空间，直接比较 score 通常没有统计意义。

## 6. 查询合成：旧引擎与当前迁移方向

`SimpleMultiModalQueryEngine` 位于 `query_engine/multi_modal.py`，在 **0.14.23 已被弃用**。弃用信息明确建议：

```python
RetrieverQueryEngine.from_args(
    retriever=retriever,
    llm=multimodal_llm,
    multimodal=True,
)
```

带引用可使用 `CitationQueryEngine.from_args(..., multimodal=True)`。提示词也由旧的：

- `text_qa_template`
- `image_qa_template`

迁移为统一：

- `chat_content_qa_template`
- 可选 `chat_content_refine_template`

默认参考 `llama_index.core.prompts.chat_prompts.CHAT_CONTENT_QA_PROMPT`，它迭代 `context_messages[].blocks` 并按 block 类型输出。

### 6.1 旧引擎的调用流（理解兼容代码）

```text
query
  -> MultiModalVectorIndexRetriever.retrieve()
  -> node postprocessors
  -> 分 ImageNode / text node
  -> text node 拼成 context_str 并格式化 prompt
  -> ImageNode 转 ImageBlock
  -> blocks.append(TextBlock(formatted_prompt))
  -> llm.chat([ChatMessage(role="user", blocks=blocks)])
  -> Response(response, source_nodes, metadata)
```

源码 `SimpleMultiModalQueryEngine.synthesize()`。`image_query()` 则走 image-to-image retrieve，再把图像与用户 prompt 交给 LLM。

## 7. QueryBundle 的多模态字段

`QueryBundle` 位于 `core/schema.py`，除 `query_str`/`embedding` 外，还支持图像查询相关状态，如 `image_path`、`embedding_image`。Retriever 会在需要时原地写入 `query_bundle.embedding`。

同一个 QueryBundle 被文本与图像异步分支共享时，应注意两个分支可能分别改写 embedding；0.14.23 的 `_aretrieve()` 直接把同一对象传给并发任务。这类实现细节是自定义多模态 retriever 时需要规避的共享可变状态。

## 8. Structured Output 与 Programs

### 8.1 BasePydanticProgram

源码：`llama-index-core/llama_index/core/types.py:103`。

契约：

- `output_cls -> Type[PydanticModel]`
- `__call__() -> Model | List[Model]`
- `acall()`
- 可选 `stream_call()/astream_call()`

它继承 `DispatcherSpanMixin`，实现类会自动得到 span。

### 8.2 主要 Program 实现

| 类 | 机制 | 源码 |
|---|---|---|
| `LLMTextCompletionProgram` | prompt + output parser | `program/llm_program.py` |
| `FunctionCallingProgram` | LLM function/tool calling | `program/function_program.py` |
| `MultiModalLLMCompletionProgram` | 图像 blocks + prompt + Pydantic parser | `program/multi_modal_llm_program.py` |
| `BaseLLMFunctionProgram` | Program 公共基类 | `program/llm_prompt_program.py` |

`PydanticProgramMode` 枚举含 `DEFAULT`、`OPENAI`、`LLM`、`FUNCTION`、`GUIDANCE`、`LM_FORMAT_ENFORCER`，但具体模型集成支持哪些模式应以其实现为准。

## 9. 多模态结构化输出调用流

`MultiModalLLMCompletionProgram.from_defaults()`：

1. 必须提供 `prompt` 或 `prompt_template_str`，二选一；
2. 必须提供 `output_cls` 或 `output_parser`；
3. 未给 parser 时创建 `PydanticOutputParser(output_cls)`；
4. 未给 LLM 时尝试 `OpenAIResponses(model="gpt-4.1")`；
5. ImageNode 转换为 ImageBlock；
6. 把 parser 绑定到 `prompt.output_parser`。

执行：

```text
program(**kwargs, image_documents=...)
  -> prompt.format(llm=llm, **kwargs)
  -> ImageNode -> ImageBlock
  -> blocks + TextBlock(formatted_prompt)
  -> llm.chat(ChatMessage(blocks=...))
  -> response.message.content
  -> PydanticOutputParser.parse(raw_output)
  -> output_cls 实例
```

示例：

```python
from pydantic import BaseModel
from llama_index.core.program import MultiModalLLMCompletionProgram
from llama_index.core.schema import ImageNode

class Invoice(BaseModel):
    number: str
    total: float
    currency: str

program = MultiModalLLMCompletionProgram.from_defaults(
    output_cls=Invoice,
    prompt_template_str="从图片提取发票字段，仅按要求输出。",
    multi_modal_llm=llm,
    image_documents=[ImageNode(image_path="./invoice.png")],
)
invoice = program()
```

这一路是“提示模型输出可解析文本，再由 parser 校验”，不等价于模型原生 JSON Schema/function calling。若 LLM 原生支持结构化输出，优先用对应集成的 `structured_predict`/Function Calling，通常比自由文本解析稳定。

## 10. 失败与安全边界

- 图像 URL 解析会访问外部资源；服务端应限制协议、域名、大小和超时，防止 SSRF/资源耗尽。
- base64 图像会显著增大内存与请求体，持久化时优先存受控 URI。
- `PydanticOutputParser` 能校验结构，不能保证字段事实正确；仍需业务规则与引用核对。
- 多模态检索的图像相似不代表答案相关，建议分模态评估 Recall@K。
- 0.14.23 的 `SimpleMultiModalQueryEngine` 已弃用，新代码不要以它为长期扩展基类。
- 模型是否支持 blocks、图像数量、mimetype、structured output，应查询具体 integration 的 metadata/实现，不能由 core 抽象保证。
