# 16 - 可观测性：CallbackManager 与 Instrumentation 双轨

> 版本范围：`llama-index-core 0.14.23`、独立包 `llama-index-instrumentation 0.5.0`。二者在源码中并存，不是同一个 API 的两个别名。

## 1. 结论先行

LlamaIndex 当前有两条观测轨道：

| 轨道 | 数据模型 | 注册位置 | 适合 |
|---|---|---|---|
| Callback | `CBEventType + Dict[EventPayload, Any]` | `Settings.callback_manager` 或组件参数 | Token 统计、调试 handler、兼容既有集成 |
| Instrumentation | 强类型 `BaseEvent` + span | 模块级 `Dispatcher` 树 | 结构化事件、调用 span、OpenTelemetry/第三方观测集成 |

同一条查询可能同时发两套信号。例如 `RetrieverQueryEngine._query()` 同时有 `@dispatcher.span` 和 `callback_manager.event(CBEventType.QUERY)`。因此：

- 配 Callback 不会自动收到所有 Instrumentation Event。
- 配 Dispatcher Handler 不会自动成为 Callback Handler。
- 两边都接入时可能重复统计同一次 LLM/Query，需要用 event/span ID 或明确的数据职责去重。

## 2. CallbackManager 轨道

源码：

- `llama-index-core/llama_index/core/callbacks/base.py`
- `llama-index-core/llama_index/core/callbacks/base_handler.py`
- `llama-index-core/llama_index/core/callbacks/schema.py`
- `llama-index-core/llama_index/core/callbacks/token_counting.py`
- `llama-index-core/llama_index/core/callbacks/llama_debug.py`

### 2.1 对象关系

```text
组件
  -> CallbackManager.event(CBEventType, payload)
       -> EventContext.on_start()
       -> CallbackManager.on_event_start()
       -> 每个 BaseCallbackHandler.on_event_start()
       -> 执行业务
       -> EventContext.on_end()
       -> 每个 BaseCallbackHandler.on_event_end()
```

`BaseCallbackHandler` 要实现四类方法：

- `on_event_start(...)`
- `on_event_end(...)`
- `start_trace(...)`
- `end_trace(..., trace_map)`

Handler 还可用 `event_starts_to_ignore`、`event_ends_to_ignore` 过滤事件。

### 2.2 层级 trace 如何形成

`CallbackManager` 使用两个 `ContextVar`：

- `global_stack_trace`：当前未结束的 event ID 栈；
- `global_stack_trace_ids`：整体 trace 的嵌套 ID 栈。

事件开始时：

1. 生成 UUID；
2. 取栈顶作为 `parent_id`；
3. 记录 `_trace_map[parent_id].append(event_id)`；
4. 广播 start；
5. 非 `LEAF_EVENTS` 入栈。

结束时广播 end，并让非叶事件出栈。`event()` 上下文管理器在异常和 `finally` 中保证结束信号；异常会放到 `EventPayload.EXCEPTION`。

### 2.3 Settings 与默认继承

```python
from llama_index.core import Settings
from llama_index.core.callbacks import CallbackManager, LlamaDebugHandler

Settings.callback_manager = CallbackManager([
    LlamaDebugHandler(print_trace_on_end=True),
])
```

无参数构造 `CallbackManager()` 时，会尝试复用 `Settings._callback_manager.handlers`。组件也常显式接收 `callback_manager`。这是一种全局默认 + 局部覆盖机制，不要在请求处理中频繁修改全局 Settings。

### 2.4 Token 统计

`TokenCountingHandler` 在 `callbacks/token_counting.py` 中处理 LLM 与 Embedding payload，维护：

- `llm_token_counts`
- `embedding_token_counts`
- prompt/completion/total token 汇总属性

Token 数是否准确取决于响应携带的 usage 或所配置 tokenizer。它适合成本统计，不是完整分布式 tracing。

## 3. Instrumentation 轨道

这里有一个容易误读的源码布局：

```text
llama-index-core/llama_index/core/instrumentation/
  ├─ __init__.py        # 从独立包重导出入口
  ├─ dispatcher.py      # 从独立包重导出 Dispatcher/Manager
  └─ events/*.py        # core 业务事件类型

llama-index-instrumentation/src/llama_index_instrumentation/
  ├─ dispatcher.py      # 真正的 Dispatcher 实现
  ├─ base/event.py
  ├─ event_handlers/
  ├─ span/
  └─ span_handlers/
```

也就是说 `llama_index.core.instrumentation.Dispatcher` 的实现来源是独立包。独立包版本在其 `pyproject.toml` 中为 `0.5.0`。

### 3.1 Dispatcher 树

入口定义于 `llama-index-instrumentation/src/llama_index_instrumentation/__init__.py`：

- `root_dispatcher`：名称 `root`，默认 Null handlers，`propagate=False`
- `root_manager`：保存所有 Dispatcher
- `get_dispatcher(name)`：按点分模块名找父级，否则父级回退到 root

例如 `get_dispatcher("llama_index.core.llms.llm")` 会创建有层级名称的 dispatcher。`propagate=True` 时事件和 span 信号沿父链传播；任何一层设为 false 即停止。

### 3.2 Event 与 Span 是两类信号

`Dispatcher` 分别维护：

- `event_handlers: List[BaseEventHandler]`
- `span_handlers: List[BaseSpanHandler]`

Event 是业务事实，例如：

- `QueryStartEvent` / `QueryEndEvent`
- `RetrievalStartEvent` / `RetrievalEndEvent`
- `SynthesizeStartEvent` / `SynthesizeEndEvent`
- `LLMChatStartEvent` / `InProgress` / `End`
- `EmbeddingStartEvent` / `End`
- `ReRankStartEvent` / `End`
- `ExceptionEvent`

这些 core 类型位于 `llama-index-core/llama_index/core/instrumentation/events/`。

Span 是函数执行边界：

```text
@dispatcher.span
function(...)
  -> span_enter(id, bound_args, instance, parent_id, tags)
  -> function
  -> span_exit(..., result)
异常:
  -> SpanDropEvent
  -> span_drop(..., err)
```

span ID 格式包含限定函数/实际类方法名与 UUID。`active_span_id: ContextVar` 保持异步任务中的父子关系。

### 3.3 DispatcherSpanMixin

`DispatcherSpanMixin.__init_subclass__()` 会扫描继承层级：

1. 找抽象方法；
2. 找基类已经 `@dispatcher.span` 的方法；
3. 子类实现/覆盖这些方法时，自动再次套入幂等 span 装饰器。

因此自定义 LLM/Retriever 等子类即使没手写 decorator，也可能自动得到 span。

### 3.4 Event 发布

```python
from llama_index.core.instrumentation import get_dispatcher
from llama_index.core.instrumentation.events.query import QueryStartEvent

dispatcher = get_dispatcher(__name__)
dispatcher.event(QueryStartEvent(query="你好"))
```

`event()` 同步广播，`aevent()` 为每个 handler 建 task 并 `gather(return_exceptions=True)`。两者都会合并当前 `instrument_tags`。Handler 异常会被吞掉，这是为了不让观测后端破坏主业务，但也意味着 handler 自身必须有独立错误监控。

### 3.5 标签、跨进程传播与关闭

独立包提供：

- `instrument_tags({...})`：在 ContextVar 中设置当前标签；
- `capture_propagation_context()`：向 span handlers 收集传播上下文，并带上 tags；
- `restore_propagation_context(context)`：在另一个执行环境恢复；
- `shutdown()`：drop 未闭合 span，然后关闭 handlers。

这些能力比 Callback trace 更接近现代 tracing，但具体 trace/export 能力仍由所安装的 handler/integration 决定。

## 4. 一次查询为何会双发

以 `llama-index-core/llama_index/core/query_engine/retriever_query_engine.py` 为例：

```text
BaseQueryEngine.query()
  -> RetrieverQueryEngine._query()       [@dispatcher.span]
       -> callback QUERY start
       -> retrieve()
            -> Retriever instrumentation/callback signals
       -> synthesize()
            -> response synthesizer:
               dispatcher SynthesizeStart/EndEvent
               callback SYNTHESIZE start/end
       -> callback QUERY end
  -> span exit
```

LLM 层更明显：`llms/callbacks.py` 的装饰器既发布强类型 LLM Event，也进入 `CBEventType.LLM` Callback。这个双发是迁移兼容设计，不应描述为 Callback 已被彻底移除。

## 5. 如何选择

### 继续用 CallbackManager

- 已有 `TokenCountingHandler`、`LlamaDebugHandler`；
- 第三方集成只提供 Callback handler；
- 只需单进程调试、token/cost 汇总；
- 需要读取传统 `CBEventType` payload。

### 优先 Instrumentation

- 新建结构化观测集成；
- 需要函数 span + 强类型业务事件；
- 需要模块级 dispatcher 过滤/传播；
- 需要 tags、异步上下文或跨进程传播。

### 双轨并用

可行，但先规定：

- Callback 只算 token/cost；
- Instrumentation 负责 trace/latency/export；
- 禁止两边各自把同一 LLM 调用累加到同一业务指标。

## 6. 自定义 Handler 骨架

Instrumentation Event Handler：

```python
from typing import Any
from llama_index.core.instrumentation import get_dispatcher
from llama_index.core.instrumentation.event_handlers import BaseEventHandler
from llama_index.core.instrumentation.events.base import BaseEvent

class PrintEventHandler(BaseEventHandler):
    @classmethod
    def class_name(cls) -> str:
        return "PrintEventHandler"

    def handle(self, event: BaseEvent, **kwargs: Any) -> Any:
        print(type(event).__name__, event)

get_dispatcher().add_event_handler(PrintEventHandler())
```

实际基类契约以独立包
`llama-index-instrumentation/src/llama_index_instrumentation/event_handlers/base.py`
为准；core 下同名模块主要承担兼容导入。

## 7. 常见误区

1. **误区：`Settings.callback_manager` 控制全部观测。**  
   它不控制模块级 Dispatcher。
2. **误区：core 的 instrumentation 是完整复制。**  
   Dispatcher 实现来自独立 `llama-index-instrumentation`。
3. **误区：Event 就等于 Span。**  
   Event 表示业务节点，Span 表示函数执行范围，两种 handler 独立。
4. **误区：handler 抛错会让查询失败。**  
   Dispatcher 主动吞 handler 异常；这提高隔离性，也可能隐藏 exporter 故障。
5. **误区：只注册在子 Dispatcher 就能收到全局事件。**  
   传播方向是当前 dispatcher 向父级，不是父级向所有子级广播；全局采集通常挂 root。
