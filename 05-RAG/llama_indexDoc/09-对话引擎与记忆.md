# 09 - ChatEngine 源码分析

> 基于 `llama-index` 0.14.23。核心源码位于
> `llama-index-core/llama_index/core/chat_engine/`，入口位于
> `llama-index-core/llama_index/core/indices/base.py::BaseIndex.as_chat_engine()`。

## 1. 统一接口与返回值

`chat_engine/types.py::BaseChatEngine` 定义四个执行入口：

```python
chat(message, chat_history=None)
stream_chat(message, chat_history=None)
await achat(message, chat_history=None)
await astream_chat(message, chat_history=None)
```

非流式返回 `AgentChatResponse`，主要字段是 `response`、`sources`、
`source_nodes` 和 `metadata`。流式返回 `StreamingAgentChatResponse`：

```python
resp = chat_engine.stream_chat("退款期限？")
for delta in resp.response_gen:
    print(delta, end="", flush=True)

resp = await chat_engine.astream_chat("退款期限？")
async for delta in resp.async_response_gen():
    print(delta, end="", flush=True)
```

流式对象不只是一个生成器。同步路径启动后台 `Thread`，
`write_response_to_history()` 消费底层 `chat_stream`、把 delta 放入队列并在结束后写
Memory；异步路径用 `asyncio.create_task()` 运行
`awrite_response_to_history()`。因此调用方应把 `response_gen` /
`async_response_gen()` 消费完；过早退出会影响完整响应和历史写入，生成器的
`finally` 才会等待后台任务并传播异常。

## 2. `ChatMode` 的实际状态

枚举定义在 `chat_engine/types.py::ChatMode`。0.14.23 的实际分派以
`indices/base.py:BaseIndex.as_chat_engine()` 为准：

| 值 | 实际类 | 数据路径 |
|---|---|---|
| `simple` | `SimpleChatEngine` | 直接调用 LLM，不检索索引 |
| `condense_question` | `CondenseQuestionChatEngine` | 历史和追问先改写，再调用 QueryEngine |
| `context` | `ContextChatEngine` | 用原始本轮消息检索，再带历史合成 |
| `condense_plus_context` | `CondensePlusContextChatEngine` | 改写追问、检索、带历史合成 |
| `best` | `CondensePlusContextChatEngine` | 当前与上一项相同，是默认值 |
| `react` / `openai` | 已移除 | 枚举仍保留，但调用会立即抛 `ValueError` |

`as_chat_engine()` 会先解析 LLM，并且无条件构造
`self.as_query_engine(llm=llm, **kwargs)`；随后 `context` 与
`condense_plus_context` 又调用 `self.as_retriever(**kwargs)`。这意味着 `kwargs`
必须同时适用于相关工厂，传入错误参数可能在真正的模式分派前就失败。

旧文档中“`best` 自动选择 ReAct/OpenAI Agent”的描述已经过期。
`REACT`/`OPENAI` 也不能继续使用；需要工具调用时应显式创建
`llama_index.core.agent.workflow.ReActAgent` 或 `FunctionAgent`。

## 3. `ContextChatEngine` 调用链

源码：`chat_engine/context.py`。

同步 `chat()` 的调用链为：

1. 如传入 `chat_history`，先执行 `memory.set(chat_history)`，替换会话历史。
2. `_get_nodes(message)` 调 `retriever.retrieve(message)`。
3. 按顺序执行每个 `node_postprocessor.postprocess_nodes(...)`。
4. `memory.get(input=message)` 取得受 token 限制的历史。
5. `_get_response_synthesizer()` 将 context template、system prompt、历史组装成
   `CompactAndRefine`。
6. `synthesizer.synthesize(message, nodes)` 生成回答。
7. 用户消息与最终回答写入 Memory，返回带 `source_nodes` 的响应。

`achat()` 使用 `aretrieve()`、`apostprocess_nodes()`、`asynthesize()` 以及 Memory
的异步接口；它不是简单在线程中包装整个同步调用。`stream_chat()` /
`astream_chat()` 仍先完成检索与 synthesizer 构造，然后返回 token 流。

若检索为空且直接调用类方法时提供了 `prev_chunks`，会复用上一批节点；
`BaseIndex.as_chat_engine()` 的普通入口没有自动管理该参数。

## 4. `CondensePlusContextChatEngine` 调用链

源码：`chat_engine/condense_plus_context.py`。

`_run_c3()` 是同步主链：

```text
memory.get(input=message)
  -> _condense_question(history, message)
  -> retriever.retrieve(condensed_question)
  -> node_postprocessors
  -> _get_response_synthesizer(history)
  -> synthesize(original_message, context_nodes)
```

需要注意两个不同的 query：`condensed_question` 用于检索，而最终 synthesizer
仍接收原始 `message`。有历史时，改写使用 `llm.complete()`；异步链
`_arun_c3()` 使用 `llm.acomplete()`。首轮、空历史或 `skip_condense=True` 时直接
使用原消息，少一次 LLM 调用。

`CondenseQuestionChatEngine` 则将独立问题交给完整 QueryEngine；两者的 prompt
注入位置和 source 返回方式不同，不能只看名称认为等价。

## 5. Memory 与 chat store

0.14.23 的 ChatEngine 默认使用新
`llama_index.core.memory.Memory.from_defaults(...)`，token 上限通常设为
`llm.metadata.context_window - 256`。`ChatMemoryBuffer` 仍可导入，但其类注释已明确
标记 deprecated，应优先使用 `Memory`。

Memory 负责“如何裁剪/组织给模型的上下文”，chat store 负责“消息按 key 如何保存”。
旧 `ChatMemoryBuffer` 展示了两层关系：

```python
from llama_index.core.memory import ChatMemoryBuffer
from llama_index.core.storage.chat_store import SimpleChatStore

store = SimpleChatStore()
memory = ChatMemoryBuffer.from_defaults(
    token_limit=3000,
    chat_store=store,
    chat_store_key="tenant-a:session-42",
)
chat_engine = index.as_chat_engine(
    chat_mode="condense_plus_context",
    memory=memory,
)
```

`SimpleChatStore` 位于 `storage/chat_store/simple_chat_store.py`，提供
`set_messages/get_messages/add_message/delete_*`，可 `persist("chat_store.json")`
并由 `from_persist_path()` 加载。它是进程内 dict 加 JSON 持久化，不具备多进程并发
控制；生产环境应换对应的独立 chat-store 集成。

`ChatMemoryBuffer.get()` 从最新消息向前裁剪，并避免让 assistant/tool 消息成为截断后
历史的开头；单条消息本身超限时仍返回该条，让底层 LLM 给出显式超长错误。

## 6. 推荐用法

```python
from llama_index.core.memory import Memory

memory = Memory.from_defaults(token_limit=6000)
chat_engine = index.as_chat_engine(
    chat_mode="condense_plus_context",
    llm=llm,
    memory=memory,
    similarity_top_k=5,
    system_prompt="仅根据检索资料回答；资料不足时明确说明。",
)

answer = await chat_engine.achat("它的退款期限呢？")
print(answer.response)
for item in answer.source_nodes:
    print(item.score, item.node.metadata)
```

## 7. 常见陷阱

- ChatEngine 实例持有 Memory，不应无隔离地作为所有 Web 用户的全局单例；每个 session
  使用独立 Memory 或独立 chat-store key。
- `chat_history=` 会覆盖当前 Memory，不是增量追加。
- `reset()` 清空该 Memory 对应的历史；共享 key 时会影响同 key 的其他使用者。
- `system_prompt` 与 `prefix_messages` 在 `ContextChatEngine.from_defaults()` 中互斥。
- `source_nodes` 是检索结果，不等于逐句可验证引用；后处理和合成可能未使用每个节点。
- 流式仅让生成阶段逐 token 返回；检索、问题改写等前置步骤仍会造成首 token 延迟。
- 多模态索引只支持 `context` 与 `condense_plus_context` 分派，路径在
  `indices/multi_modal/base.py`，不要假设所有文本模式都可用。
